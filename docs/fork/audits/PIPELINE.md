# 持续审查流水线（PIPELINE）

老板令：持续审、泛范围审、多模型验证、确认的写进带日期修复文档。目标是项目长期稳定（开发层面不出问题、长期工作不退化）。

## 循环结构
1. **发现轮**：并行派 N（4~6）条 **DeepSeek v4.1 Flash** 审查线。每条只给"角度 + 纪律 + 产出格式"，**不给范围上限**（项目大且是 AI 项目，不同角度才审得出不同的问题）。允许自己决定看哪里、跟着线索走。
2. **对撞轮**：发现轮报回后，把每条结论交给 **千问 3.8 Flash**（对抗：找反例、能否打穿）与 **Kimi K3**（深审：该不该算问题、有没有更根本的解法）。两边都站得住才进档。
3. **成档**：确认的条目写进 `docs/fork/audits/<日期>-*.md`（带日期、证据、影响、修法、状态）；同时追加一行到 `decisions.jsonl`。
4. **修复**：红测 → 补丁 → 绿 → 全仓检查；在独立 worktree 里做，不污染主工作区。
5. **心跳**：每 30 分钟推进一轮（收线 / 派线 / 并档 / 修缺陷），从不空转。

## 已用过的角度（每轮换新的，避免审美疲劳）
- R2（2026-09-14 深夜起，老板点名）：**长会话退化**——同一个窗口跑很久之后，工具调用/出字/速度/token 全线变慢。要求量化（把"每次回合要做的事"随转录长度的伸缩曲线量出来），不是靠感觉。\n- R1（2026-09-14 夜）：性能热路径 / 影响模型智能的面 / 模型运行时表现 / 长期运行稳定性 / 数据与协议正确性
- 已完成的行级深读面（不重复劳动，但发现我的结论有错要报）：agent-session 通知链、stall-watchdog、turn-liveness、orphan-process-journal、venv-in-use、pending-delivery-queue、session-lease、cron-jobs、agent-messages、daemon-protocol、session-info-disk-cache、compaction 渲染/解析

## 派活纪律（每条线都要带）
- 只读：不许改仓库（产出写 /tmp/audit_r/<round>/<lane>.md，心跳写同目录 <lane>.heartbeat）
- 证据纪律：不许把注释当证据；"不存在/无影响"必须附正控；验不了写 unverified
- 冻结 SHA：本轮 = 审查时点的 HEAD，命令写死 SHA 不用 HEAD
- 收尾必须回话给 parent（≤12 行）：Top 结论 + 证据路径 + 未完成项
- **禁止触发全机停机/清扫（2026-09-15 加，事故：把老板正在用的 daemon 一起停了；R13 实测更正——不只是 --force）**：任何审查/施工线**不许**跑 `prime-agent shutdown`（**任何变体，含普通形式**：R13 用真函数实测 `planShutdownAll(infos,false)` 会把带 119 条活会话的 daemon 列进停机计划，且 `daemon` 已在 REMOVED_COMMAND_NAMES 里、没有 scoped 替代）、`doctor --fix`、`daemon ps -k`。原因是 socket 路径按 uid 落在 tmpdir（`daemon-socket.ts:282-285`），只换 HOME/agentDir **隔离不了 socket**，而 `--force` 是全机发现（`daemon-ps.ts:421-495`）。要测停机行为必须在**自己的 TMPDIR** 下起自带 socket 的 daemon，或直接对假 transport 测。事故链：round-06 tool-silence 线在 /tmp/wt-toolfix 跑 `shutdown --force` → 19:04:32 共享 daemon（501）被停 → 客户端按设计进入终局态、19:48 老板手开才恢复。
- **并发上限与孤儿清扫（2026-09-15 加，事故：把机器 CPU 打到 300%）**：同时最多 **3~4 条**线（今晚一度跑到 6~10 条，是我违规）；每条线的探针**自带短超时（≤60s）**、禁止给子进程传小时级参数；每轮收线后必须 `ps -A -o pid,pcpu,ppid,command | grep tsx` 扫一遍 **ppid=1 的孤儿**并清掉。事故实况：6 个孤儿探针（同一脚本、传了 3600000ms）各烧 ~50% CPU 持续十分钟。
- **合并推送要批量（2026-09-15 加，血泪）**：逐条小提交立刻推送会让远端累积大量 `cancelled` run（同分支新推送会取消在跑的旧 run）。**改成攒够 2~3 条修复再推一次**，让每次推送都有一个"跑完的结论"，老板在页面上看到的才是干净的历史。取消不是失败，但会淹没真正的红。
- **provider 空回包的处理（2026-09-15 加，两起）**：`bailian/deepseek-v4.1-flash` 线偶发"连续三次空响应"终局失败（今晚 2 起：断连 UX 线、文案诚实性修复线）。规律：**不重试同一模型**，直接换型重派（千问 3.8 Flash 接得稳、已验证），并把已取到的证据路径交给新席避免重复取证。派活时若任务重（多文件+多测试），优先给千问或 GLM。
- **收尾顺序铁律（2026-09-15 加）**：**先写报告文件、再回话**。今晚 4 条线在各种半路死亡（看门狗判死 1、RLM 取消 2、provider 连续空回包 1）；凡"报告已落盘"的都没丢结论，凡"只写了心跳"的就只剩心跳。另：父线被取消时**必须去翻它子线的产出**（已救回 1 条带真缺陷的报告）。
- **反卡死纪律（2026-09-15 加，血泪）**：一条审查线被看门狗以"静默 900s"判死、产出为零（报告与心跳都没写）。凡派线必须写死：①每步落心跳（先写发现再继续）②任何单次命令/脚本 ≤60s，大扫描分批 ③每 5~8 步把已确认结论写进产出文件 ④20~30 分钟收口。重派时**拆窄**（同一角度拆成两条线）。
- **测试环境**：跑任何套件都要 unset 泄露变量，除了 RLM_*/PRIME_AGENT_*/PI_*，还有 **RLM_MAX_DEPTH**（实测：`agent-session-recursion.test.ts` 会因它多出 1 条失败；unset 后 121 项全绿）
