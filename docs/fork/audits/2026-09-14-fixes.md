# SCAN-OFFSET（P1）`readFileLines` 对跨 chunk 长行漏计字节 ⇒ 活会话计数错 + 每次追加白读

**机制**（`utils/file-lines.ts:65-101`）：`consumed += end - start + 1`（`:90`）只计"终结该行的那一小段"，先前 chunk 存进 `pendingParts`（`:75-78`）的字节**从不计入** ⇒ `endOffset` 系统性偏小。
**实测漂移**：98.8MB 文件最终 `endOffset` 比文件小 **17.2MB（16.6%）**；63MB 小 **24.4MB（38.6%）**；12.5MB 小 **3.9MB（31.4%）**（另一席位独立数字一致）。

**后果①用户可见的数据错**：resume 判定用 `cached.scan.offset <= stats.size`（`session-manager.ts:1248`）⇒ 脏 offset 仍被视为合法，下一次 append 从**错误位置重扫、把已数过的行再数一遍**。
实测（12.5MB 活会话，追加 1 行后）：`messageCount` 2002 → **2546（+27.1%）**；`inputTokens` 368,221,433 → **151,920,366（−59%）**；清缓存后全量为 2003（真值）。
**只影响持续 append 的活会话**——正是老板在 agents 视图上盯着的那一行；磁盘 durable 摘要是对的，错的是内存那行。

**后果②隐性浪费**：每次 append 白读漂移窗口（13MB 文件重扫 2079/6370 行 = 2.3ms，本应 2 行 0.3ms）；60~100MB 会话每次白读 17~24MB。▶ 会话越活、巨型 tool result 越多，漂移越大——**纯浪费且随会话大小增长**。

**修法（未实施 → 已派修）**：flush pending 行时把缓冲字节计入 `consumed`（或以"流内已读字节 − pending 字节"推导）；对既有 scan 状态加 **offset 一致性校验**。修好后：数字恢复正确，且 append 读量从 MB 级降到 ~200B。
